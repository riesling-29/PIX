# PIX 도메인 검토 방식과 검토표

작성일: 2026-09-13. 상태: **도메인 검토 절차 채택, 개별 예제는 미검토·미실행**.
연결: [상세 개발 계획](2026-09-13_PIX_DETAILED_DEVELOPMENT_PLAN.md).
2026-09-13 사용자는 이 방식을 플랜에 기록하고 이후 하나씩 개발하기로 했다.
이번에는 계획 기록까지만 요청했으므로 기능 구현·신규 테스트 작성/실행은 시작하지 않는다.
운영 절차 채택은 아래 waiting 등 개별 지표 정의나 예제 결과의 채택을 뜻하지 않는다.

## 1. 목적과 검토 단위

검토 단위는 파일·commit·함수보다 **도메인 질문 하나에 답하는 계산 묶음**으로 둔다.
예를 들어 공유 이벤트의 빈도, 특정 시점의 객체 상태, 공동 실행의 적합성, 응답 기한의 위반 여부다.

Chanta Minero 선생님은 계산이 의도한 업무 질문에 답하는지, 모델의 허용 행동·모집단·시간 해석이
타당한지 판단한다. Vera는 선택지·작은 입력·예상 답과 근거를 준비하고 구현·독립 검산·실행 결과를 연결한다.
사용자의 검토가 일반적인 정확성·최적성·성능을 증명하는 것은 아니며, 이 검증 책임을 사용자에게 넘기지 않는다.

## 2. 개발 전과 개발 후를 분리하는 흐름

| 단계 | 준비할 자료 | 판단/다음 행동 |
| --- | --- | --- |
| 의미 초안 | 업무 질문, 계산 범위, 정의 후보, 작은 입력과 예상 답, 반례 | 어떤 해석을 채택할지 또는 기존 합의가 적용되는지 확인 |
| 기대값 고정 | 선택한 정의·fixture·예상 값/성질과 작성 시점 | 구현 출력에 맞춰 기대값을 뒤늦게 고치지 않음. 오류를 발견하면 변경 이유·이력을 남김 |
| 구현·검산 | Native 계산, 독립 oracle·경계·실제 데이터 시험 | 합의한 범위 안에서 구현·리팩터링·회귀 수정을 진행 |
| 결과 검토 | 예상/실제/차이, 포함·제외·불명 대상, event/object/model 근거 | 의미가 맞는지와 구현이 맞는지를 별도 판정 |
| 회귀 반영 | 채택 사례·새 반례·profile/코드/입력 판본·검토 기록 | 이후 동일 조건에서는 자동 검사, 의미가 바뀌면 영향 범위를 다시 검토 |

예상 답은 반드시 사용자가 처음부터 작성할 필요가 없다. Vera가 논리·수계산·독립 방법을 붙여 초안을
제시하고 선생님이 확인할 수 있다. 정확한 최적해를 모르면 기대 성질·알려진 해·하한/상한을 쓰고
모르는 값은 알 수 없음으로 남긴다. 발견 모델의 그림 하나를 유일한 정답으로 고정하지 않는다.

## 3. 매번 보는 검토표

본문은 한두 쪽을 목표로 하고 긴 로그·JSON·테스트 기록은 링크한다. 분량과 사례 수는 검토 가능성에 맞춰 조절한다.

| 항목 | 내용 |
| --- | --- |
| 질문 | 이번 계산으로 무엇을 판단하려는가? |
| 해석 | 모집단·분모·가중치·순서·관계·시간·종료·모델 출처 |
| 작은 입력 | 눈으로 셀 수 있는 event/object 표, 관계도·시간표·모델 |
| 예상 답 | 구현 전에 고정한 값 또는 성질, 이유, 실패해야 하는 반례 |
| 실제 결과 | 값·상태·대상·제외·unknown·한도, 중간 계산·witness |
| 차이와 영향 | 기대값/upstream/이전 버전과의 차이, 변경되는 profile·후속 계산 |

항상 포함할 관점은 정상 사례, 해석이 갈리는 경계, 잘못된 구현을 잡는 반례, 정보 부족이다.
독립적인 변화 하나만 준 비교 사례가 유용하다. 예를 들어 ID만 치환하면 variant가 같아야 하고,
참여 객체의 연결을 바꾸면 채택한 동치 정의에 따라 달라져야 한다.

## 4. 검토 결과는 두 축으로 기록한다

| 축 | 기록할 상태의 예 |
| --- | --- |
| 도메인 판단 | 미검토 / 정의 채택 / 별도 profile 필요 / 정의 수정 / 근거 부족·보류 |
| 구현·검증 | 미실행 / 해당 사례 통과 / 불일치 / 부분 계산 / 실사용 범위 미검증 |

예를 들어 정의 채택 + 미실행은 구현 완료가 아니다. 테스트 통과 + 도메인 미검토도 사용자가 그 해석을
채택했다는 뜻이 아니다. 실제 사용자 발언 없이 사용자 판단란을 채우지 않는다.

PM4Py/OCPA 비교값이 다르면 **정의/입력 차이, PIX 결함, 참조 구현 문제, 미확인**으로 나눈다.
두 라이브러리와 값이 같다는 이유만으로 정답으로 삼지 않는다. 결함을 발견해 기대값을 고칠 때는
원래 기대값과 수정 근거를 함께 남긴다.

## 5. 개발 재개 후 적용할 검토 운영

- 새로운 의미 선택, 기존 정의 변경, 여러 계산에 영향을 주는 정책을 우선 검토 대상으로 올린다.
- 기존에 채택한 정의의 구현·리팩터링·오류 수정은 자동 검증으로 진행한다. 모든 commit에 별도 승인을 요구하지 않는다.
- 미정인 도메인 선택은 무응답으로 채택하지 않는다. 필요한 결정이 미정이면 그 결정에 의존하는 부분을 보류하고 독립적인 구현·검산은 계속한다.
- 이후 보고는 변경된 결과·새 반례·아직 불명확한 부분을 중심으로 한다. 이미 확인한 전체 내용을 매번 다시 검토하도록 하지 않는다.
- 진행 여부 판단에는 필요하면 범위 유지·보류·무변경도 포함한다. 이미 적합한 계산을 단지 진척을 보이려고 바꾸지 않는다.

검토 주기는 달력보다 계산 의미가 준비되는 시점에 맞춘다. 작은 검토 묶음들을 모아 확인할 수 있고,
공유 계약에 영향이 큰 결정은 해당 구현을 넓히기 전에 확인한다. 주당 시간 절감 효과는 아직 측정하지 않았다.

## 6. 재사용할 현재 PIX 자료

[모델 평가 가이드](../user-guide/NATIVE_MODEL_EVALUATION_GUIDE.md)와
[예제 생성 코드](../../examples/model_evaluation.py)는 이미 원본 입력·참여 분포·joint alignment 단계·
지표 분자/분모·규칙 결과의 검토 보고서를 생성한다.

로컬에 `.artifacts/v040/demo/review.md`와 OCDFG·PN·OCPN HTML이 있으며,
이는 **2026-09-10 합성 입력의 기존 실행 결과**다. 이번 제안에서 새로 실행한 자료는 아니다.
실제 객체·모델 근거를 보는 출발점으로 활용하되 모든 계획 기능을 지원하는 검토 화면으로 표현하지 않는다.

첫 운영안은 Markdown 검토표 + 기존 HTML graph + 결과 JSON/실행 기록이다.
현재 DFG/OCDFG graph adapter는 computed만 받는다. Partial 지표의 설명은 검토표에서 명확히 표현하고,
전용 화면이 필요하면 VIEW-01 작업으로 확장한다. 별도 dashboard 구축을 선행 조건으로 두지 않는다.

## 7. 작성 예제 — waiting의 기준 시점

**검토 ID:** DR-PERF-001. **계획 연결:** PERF-01/03.
**도메인 상태:** 미검토. **구현 검증:** 이 검토표를 이용한 실행은 하지 않음.
**질문:** 모든 입력이 준비된 뒤 실제 활동을 시작하기까지의 시간을 측정하려는가?

입력 준비 시각 A=09:00, B=09:10, 활동 시작=09:15, 완료=09:25라고 가정한다.
해당 시각들이 관측값으로 제공되었다고 가정한 합성 예제다.

| 정의 후보 | 손계산 기대값 | PIX 실제 결과 |
| --- | ---: | --- |
| 모든 입력 준비 후 시작: start−max(arrival) | 5분 | 미실행 |
| 첫 입력 도착 후 시작: start−min(arrival) | 15분 | 미실행 |
| 활동 처리 구간: complete−start | 10분 | 미실행 |

이 셋은 질문이 다르다. OCPA OPERA 기준 판본의 waiting 식은 두 번째이며,
그 대응 구현과 별도 PIX 지표의 이름을 구별하는 안은 상세 개발 계획의 PERF 절을 따른다.

| 바꿀 조건 | 구현 전에 정할 기대 성질 | 실제 검증 |
| --- | --- | --- |
| A만 08:50으로 앞당김 | 첫 정의는 5분 유지, 두 번째는 25분으로 변함 | 미실행 |
| B를 09:15로 늦춤 | 모든 입력 준비 후 시작은 0분 | 미실행 |
| Start 시각을 제거 | 두 waiting과 service를 관측값으로 계산할 수 없음. 임의 0 금지 | 미실행 |
| 보정 replay token만 도착 시각이 없음 | 가상 token에 실제 준비 시각을 지어내지 않음 | 미실행 |

**선생님이 판단할 내용:** 원하는 업무 질문, 기본 표시명, 두 정의의 병행 필요성,
결측·보정 token을 포함하는 집계의 처리. 실제 판단 기록은 아직 없다.
채택 후 고정한 fixture·기대값을 `tests/performance/test_metric_definitions.py` 및 token 성능
검증에 연결하고, 새 실행 결과를 채워 다시 검토한다. 테스트 파일명은 개발 계획상 제안이다.

## 8. 다음 영역에 사용할 반례

- **공유 이벤트 빈도:** 승인 event 하나가 주문 두 개에 연결될 때 고유 event=1, 주문 occurrence=2.
  어느 값이 질문에 맞는지와 표시된 분모를 확인한다.
- **공동 참여:** 결합을 유지해야 한다는 명시적 규범이 있을 때 Order–Item 짝을 교차시킨다.
  객체별 sequence의 수용과 그 결합 규범의 충족을 구분한다. 교차 자체를 모든 로그의 오류로 단정하지 않는다.
  현재 모델이 그 규범을 표현하지 못하면 표현 불가를 먼저 기록하며 alignment가 알아서 검출한다고 가정하지 않는다.
- **과거 상태:** Pay가 당시 승인 상태를 요구한다는 규칙 아래에서, Draft→Approved 이력의
  승인 전 Pay를 최종 approved 값으로 소급 통과시키지 않는다.
- **열린 관측:** Request의 응답 기한 전, 아직 유효한 응답이나 확정 위반이 없으면 pending.
  유효 응답·첫 응답 정책·시간창·관측 완결성을 바꾸며 어떤 조건에서 판정이 달라지는지 확인한다.

## 9. 효과 확인과 수정 조건

이 방식은 구체적 예제로 의미를 설명하고 별도 계산법으로 검증하는
[Specification by Example](https://martinfowler.com/bliki/SpecificationByExample.html)의 접근을
PIX 상황에 적용한 운영 방식이다. 절차는 채택했지만 효과는 아직 측정하지 않았다.
예제만으로 모든 입력의 정확성을 보장하지 않으므로 계약·반례·독립 검산과 함께 사용한다.

초기 검토에서 코드 설명 없이 모집단·허용 행동·판정 근거를 판단할 수 있는지,
같은 의미 문제로 반복 재작업하는지, 검토 대기가 어디서 발생하는지 기록한다.
검토가 어렵거나 반복 오해가 줄지 않으면 표의 구성·사례 크기·검토 시점을 바꾼다.
검토 시간 절감률·오류 감소율은 현재 알 수 없음이다.

판단은 기록한 정의/profile·fixture·모델·코드·실행 환경에 유효하다.
새 반례·정의 변경·표현 불가·원본 의미 손실이 확인되면 해당 채택/정확성 판단을 재검토한다.

## 10. 채택한 방향

**업무 질문과 작은 반례를 먼저 확인하고, 동일 사례의 실제 PIX 결과를 검토한 뒤,
그 판단을 반복 가능한 회귀 검증으로 축적하는 방식**으로 개발과 도메인 검토를 연결한다.
